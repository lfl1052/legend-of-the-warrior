# Codex 游戏开发工作流与 Prompt 模板

项目专业角色说明见 `docs/agents/README.md`。当任务涉及玩法、关卡、Godot 地编实现或试玩评审时，先按根 `AGENTS.md` 的角色路由读取对应文件。

## 什么写进文件，什么放在对话里

| 内容 | 放置位置 | 示例 |
| --- | --- | --- |
| 长期工程规则 | `AGENTS.md` | Godot 版本、静态类型、架构约束、测试要求 |
| 已确认的玩法设计 | `design/gdd/` | 战斗规则、敌人职责、关卡节奏、成长公式 |
| 架构决策 | `docs/architecture/` | Event Bus、存档协议、场景资源契约 |
| 迭代任务和验收标准 | `production/stories/` | 一个可独立实现和验证的 Story |
| 当前多轮任务状态 | `production/session-state/active.md` | 当前目标、已完成步骤、阻塞项 |
| 当次任务要求 | Codex 对话 Prompt | 本次要改什么、不改什么、怎样算完成 |

Prompt 不是项目文档的替代品。稳定规则写入文件后，每次对话只需要补充本次任务的目标、范围和验收条件。

## 推荐开发循环

```text
只读调查
→ 对照 GDD 找差异
→ 提出小范围实施计划
→ 确认修改范围
→ 实现脚本/场景/数据
→ 自动化测试
→ 实际运行和截图
→ 汇报结果与风险
```

每次优先完成一个可玩的垂直切片，不按“先写完全部脚本、最后再拼场景”的方式推进。

## 模板一：只读项目审计

```text
请只读分析当前项目根目录，暂时不要修改文件。

任务目标：<要了解的问题>

请检查：
1. 对应 GDD、Story 和当前实现。
2. 涉及的脚本、场景、数据、资产和测试。
3. 当前调用链、状态流转和跨系统依赖。
4. 现有未提交修改是否与任务重叠。
5. 缺失功能、设计冲突和回归风险。

输出：
- 当前实现
- 设计差异
- 建议修改范围
- 验证方案

禁止修改、恢复、删除、暂存或提交文件。
```

## 模板二：玩法功能实现

```text
请实现：<功能名称>。

玩家体验目标：
<玩家应该观察、决定和执行什么>

玩法规则：
1. <规则一>
2. <规则二>
3. <失败和恢复>
4. <奖励和反馈>

修改范围：
- <允许修改的系统/场景/数据>

非目标：
- <本次不实现的功能>
- 不修改 addons/godot_ai 和 addons/gdUnit4。
- 不覆盖无关的未提交修改。

验收条件：
1. <可观察结果>
2. <边界条件>
3. 相关单元和集成测试通过。
4. 在 640×360 下实际运行并提供代表状态截图。
5. 汇报修改文件、测试结果和未验证风险。

修改前先给出实施计划和拟修改文件；范围明确后再实施。
```

## 模板三：关卡垂直切片

```text
请完成 <关卡名称> 的 <区段名称> 垂直切片。

教学目标：<本区段教会玩家什么>
主要压力：<空间、敌人、时间、资源或操作压力>
完成条件：<玩家如何结束本区段>
失败恢复：<检查点和重试成本>
奖励：<完成后得到什么>

遭遇节奏：
1. Introduce：<安全展示>
2. Confirm：<要求主动使用>
3. Combine：<与旧机制组合>
4. Stress：<提高决策压力>
5. Test：<独立完成>
6. Payoff：<奖励和离场>

要求检查：
- 相机是否在敌人造成威胁前展示其轮廓。
- 平台、TileMap 和碰撞是否公平。
- 前景、HUD 和特效是否遮挡攻击提示。
- 关卡是否存在不可达路线或无意义回跑。
- 装载、通路、冒烟和视觉测试是否覆盖本次修改。
```

## 模板四：Bug 修复

```text
请修复：<Bug 描述>。

复现步骤：
1. <步骤>
2. <步骤>

期望行为：<正确结果>
实际行为：<错误结果>

要求：
1. 先定位根因，不只处理表面现象。
2. 检查存档、状态机、输入、物理和场景切换边界。
3. 添加能够在修复前失败、修复后通过的回归测试。
4. 不改变无关玩法参数。
5. 实际运行复现路径并汇报结果。
```

## 模板五：完成前验证

```text
请对当前任务做完成性检查，不新增功能。

检查：
1. git diff 是否只包含任务范围内的修改。
2. Godot headless import 是否无脚本和资源错误。
3. 相关单元、集成和冒烟测试是否通过。
4. 640×360 下的关键状态是否已实际运行和截图。
5. 是否存在存档兼容、资源 UID、输入焦点、碰撞或性能风险。
6. GDD、Story、项目地图或测试文档是否需要同步。

输出：
- 已验证内容
- 失败项
- 未验证项
- 建议是否可以提交

除修复明确发现的问题外，不扩大任务范围。
```

## AI 应用技术是否需要加入游戏

当前开发流程不要求把 RAG、向量数据库、LangChain 或微调代码加入游戏。

- Codex 搜索本地代码和文档，是开发时的上下文检索。
- `AGENTS.md` 和 GDD 提供稳定项目上下文。
- 每次对话 Prompt 提供本次目标和验收标准。
- Godot MCP 用于开发期编辑器控制和验证。

只有明确开发下列运行时功能时，才需要单独设计 AI 应用架构：

- NPC 生成式对话。
- 游戏百科或剧情知识问答。
- 玩家自然语言指令。
- 自动关卡或剧情生成。
- 联网的智能客服、社区或运营助手。

这类功能应放在独立服务中评估模型调用、成本、延迟、内容安全、离线降级、隐私和存档一致性，不能仅靠增加一段 Prompt 完成。
